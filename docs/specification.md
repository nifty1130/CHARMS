## 1. 概要

WebRTC を使った映像の共有・切り替えシステム。専用機材を使わず、端末のブラウザだけで動く。インターネットのない LAN でも使え、インターネットがあれば別のネットワークの端末ともつながる。

設計の原則:

- **サーバーに頼らない**: 端末同士が直接つながる。QR コードを使えば、接続の打ち合わせ（シグナリング）にもサーバーを使わない
- **オフライン**: アプリ本体は端末に保存され（PWA）、当日はインターネットなしで起動する
- **オンラインなら、もっと手軽に**: インターネットにつながるときは、合言葉だけでつなげ、切れても自動で戻る。STUN / TURN を使い、直接通信できない端末同士もつなぐ。使えなければ、何もせずに QR コードと LAN 内だけの動作に戻る
- **どの端末でも**: ブラウザの標準機能だけで作る
- **詳しくない人でも**: 画面の言葉は日本語で、手順は画面が案内する

## 2. 役割

| 役割 | 画面での名前 | ID | 台数 | すること |
|---|---|---|---|---|
| Host | ホスト | `host` | 1台 | 全端末とつながる中心。端末の管理、映像接続の取り次ぎ、切り替え操作 |
| Camera | カメラ | `cam1`〜 | 何台でも | 端末のカメラ、または画面の映像を送る |
| Admin | テロップ | `adm1`〜 | 何台でも | 文字を描いた映像を送る（文字版のカメラ） |
| Monitor | モニター | `mon1`〜 | 何台でも | 選ばれた映像を全画面で映す |
| Controller | スイッチャー | `ctrl1`〜 | 何台でも | どの映像をどのモニターに映すかを切り替える |

ID はホストが接続順に割り当てる。名前は「カメラ 1」のように自動で付き、あとから変えられる。端末が自分で決めた名前はその端末に保存され、次につないだときにも使われる。

## 3. つながり方の全体像

```
        制御（DataChannel）                 映像（端末同士が直接）
  ┌──────────────┐
  │    ホスト    │◀── 確認用の小さな映像 ──┐
  └──────────────┘                        │
    ▲    ▲    ▲    ▲                 ┌─────────┐ ── 本番用の映像 ──▶ モニター
    │    │    │    │                 │ カメラ  │
 カメラ モニター スイッチャー テロップ   │ テロップ│ ── 確認用の小さな映像 ──▶ スイッチャー
                                     └─────────┘
```

- すべての端末は、ホストと1本の DataChannel でつながる（QR コード、または合言葉で開通）。
- 映像は、送る端末と受ける端末が直接つながる。ホストは打ち合わせ（SDP）を取り次ぐだけで、映像そのものは中継しない。
- そのため、ホストの端末が非力でも映像の品質には影響しない。また、ホストが落ちても、すでにつながっている映像は出続ける。

## 4. QR コードでの接続

ホストと端末をつなぐ最初の1本だけ、QR コードを使う。実装は [`src/lib/rtc/`](../src/lib/rtc/) の `PeerLink`。

### 4.1 手順

両方の端末が同じことをする（どちらが先でもよい）。

1. 自分の接続情報を集めて、QR コードとして表示する
2. 相手の QR コードをカメラで読み取る
3. 両方が相手の QR を読み取った時点で開通する

片方が先に読み取り、もう片方が数十秒遅れても開通する。

### 4.2 しくみ（対称接続）

通常の WebRTC は、片方が Offer を作り、もう片方が Answer を返す。QR では往復のやり取りに順番の制約が出るので、次のようにしている。

- 両方の端末が Offer を作る（`setLocalDescription`）
- 相手の QR の情報から、相手側の SDP を **Answer として組み立て**、`setRemoteDescription` する
- DTLS の役割（どちらがサーバー役か）は、証明書のフィンガープリントの大小で決める。両方の端末が同じ結論になるので、打ち合わせは要らない
- DataChannel は、両端で同じ ID を指定する方式（`negotiated: true, id: 0`）で作る

ブラウザが作った自分側の SDP は、一切書き換えない。

### 4.3 QR に入れる内容（パケット バージョン 1）

| 位置 | サイズ | 内容 |
|---|---|---|
| 0 | 1 | マジックバイト `0x51`（'Q'） |
| 1 | 1 | バージョン（下位3ビット）= 1 |
| 2 | 32 | DTLS フィンガープリント（SHA-256） |
| 34 | 1 + n | ICE の ufrag（長さ + ASCII） |
| … | 1 + n | ICE の pwd（長さ + ASCII） |
| … | 7 または 19 ずつ | ICE 候補（フラグ 1 + アドレス 4/16 + ポート 2）を0個以上 |

候補のフラグ: bit0-1 アドレスの種類（0: IPv4 / 1: IPv6 / 2: mDNS）、bit2 プロトコル（0: UDP / 1: TCP）、bit3 種類（0: host / 1: srflx）、bit4-5 TCP の接続方式、bit6 中継（1: relay。bit3 より優先）。

- 候補は UDP だけを、最大6件入れる。srflx（STUN で調べた外側のアドレス）と relay（TURN の中継用アドレス）は、あれば必ず1件ずつ入れ、残りを host（端末自身のアドレス）に IPv4 → mDNS → IPv6 の優先順で割り当てる。他の端末から届かないアドレス（IPv6 リンクローカルなど）は入れない
- パケットは **Base45**（RFC 9285）で文字列にして QR に入れる。QR の英数字モードに収まる文字だけを使うので、読み取りライブラリによる文字化けがなく、Base64 より QR が小さい
- IPv4 候補1件で 71 バイト（QR の文字数は 107 文字）。6件でも 106 バイト（159 文字）

### 4.4 安全のための検査

- QR から来た ufrag / pwd は、SDP に埋め込む前に文字の種類を検査する（改行を混ぜて SDP に行を差し込まれるのを防ぐ）
- 接続の相手は DTLS のフィンガープリントで確かめられる。両方の画面に同じ4桁の「確認コード」が出るので、目で見比べることもできる
- 自分の QR、CHARM Point 以外の QR、バージョンの違う QR は、分かる言葉で断る

### 4.5 QR を使わない方法

- **同じ端末の中**: 同じブラウザの別タブ同士は `BroadcastChannel` で接続情報を自動で交換する（1台の PC でホストとスイッチャーを開く場合など）。他の端末には届かない
- **カメラがない端末**: QR に入れるのと同じ文字列を、コピーして貼り付ける

### 4.6 QWBP との関係

パケットの構造、フィンガープリントの比較による役割の決定、確認コードは [QWBP](https://github.com/magarcia/qwbp) にならっている。ただし QWBP は ICE の ufrag / pwd をフィンガープリントから計算し、ブラウザが作った SDP を書き換えて使う。Chrome はこの書き換えを将来拒否すると告知しているため、CHARM Point ではブラウザが作った値をそのままパケットに入れている（バージョン番号を 1 にして区別。QWBP とは互換性がない）。

### 4.7 STUN / TURN

同じ LAN にいない端末同士（または端末同士の通信を止めている Wi-Fi）をつなぐための仕組み。実装は [`ice.ts`](../src/lib/charms/ice.ts)（アプリ）と [`worker/ice.ts`](../worker/ice.ts)（配信元）。

| 種類 | 役目 | サーバー |
|---|---|---|
| STUN | ルーターの外側から見た自分のアドレスを調べる。多くの家庭用ルーター越しに、直接つながるようになる | `stun.cloudflare.com`（無料） |
| TURN | 直接つながらないときに、通信を中継する | Cloudflare Realtime TURN（鍵が必要。通信量で課金） |

- アプリは、つなぐ前に配信元の `/api/ice` へ問い合わせて、サーバーの一覧を受け取る。待つのは最大 2.5 秒。届かなければ（オフライン、または API のない場所で配信している）、一覧は空になり、LAN 内だけでつなぐ
- TURN の長期の鍵は Worker の中だけにあり、ブラウザには 24 時間だけ有効な認証情報を発行して渡す。鍵を登録していなければ、STUN だけを返す
- 一覧は 10 分間使い回す。取得に失敗したときは 30 秒あけてから試し直す
- どの経路を使うかは ICE が自動で選ぶ（直接 → 外側のアドレス → 中継 の順に優先）。中継を通る通信も、端末同士で暗号化されている（DTLS / SRTP）ので、中継サーバーは中身を読めない
- 候補の収集は、中継用の候補が届いてから 0.4 秒、または最大 4 秒で切り上げる（届かない経路の時間切れを待たない）

### 4.8 合言葉・招待リンク（ルーム）

インターネットにつながるときに、QR コードの代わりに使える方法。実装は [`room.ts`](../src/lib/charms/room.ts)（アプリ）と [`worker/room.ts`](../worker/room.ts)・[`worker/room-logic.ts`](../worker/room-logic.ts)（配信元）。

しくみは QR コードと同じで、**受け渡しの手段だけが違う**。QR に入れるのと同じ文字列（4.3）を、配信元の「ルーム」を通して交換する。交換が済めば、あとは QR でつないだときとまったく同じ（端末同士が直接つながり、ルームは使わない）。

```
端末 ── offer（端末の接続情報）──▶ ルーム ── join ──▶ ホスト
端末 ◀── answer（ホストの接続情報）── ルーム ◀── answer ── ホスト
以降、端末とホストが直接つながる（DataChannel）。端末はルームから離れる
```

- **合言葉**: 6桁の数字。ホストが乱数で作る。ルームは合言葉ごとに1つ（Cloudflare Durable Objects）で、`/api/room/<合言葉>` に WebSocket でつなぐ
- **ホストの鍵**: ホストは、合言葉と一緒に乱数の鍵を作って保存しておく。ルームは最初に来たホストの鍵を覚え、同じ鍵を持つホストだけを受け入れる。ホストのページを読み込み直しても同じ合言葉を使い続けられ、他人に合言葉を横取りされない。ホストがいなくなって12時間経つと、その合言葉は空く
- **端末**: 合言葉を知っていれば申し込める。ホストがまだ来ていなければ、来るまで待つ
- **招待リンク**: `https://…/?room=<合言葉>`。開いて役割を選ぶと、合言葉の入力を省いてつながる。役割のページを直接指すリンク（`/monitor/?room=…`）なら、役割の選択も要らない
- **配信ソフト用の出力リンク**: `/monitor/?room=…&clean=1&sound=1&name=…`。操作パネルや文字を出さず、音を最初から出すモニターとして自動でつながる。OBS などの「ブラウザ」ソースに貼り付けて使う
- **ルームに届かないとき**（オフライン、または API のない場所で配信している）: ホストの画面には「合言葉は使えません」と出て、QR コードだけでつなぐ。間をあけて自動で試し直す

安全のための考慮:

- ルームを通るのは接続情報の文字列だけで、形式（Base45 の文字、長さ）を検査してから取り次ぐ。映像・音声・操作の内容は通らない
- 端末からホストへは申し込みだけができ、他の端末宛てには送れない
- WebSocket は、アプリ自身のページから開かれたもの（`Origin` が同じ）だけを受け付ける
- 合言葉は6桁なので、当てずっぽうで入れてしまう可能性はゼロではない。ホストは申し込みを自動で受け入れるので、つながった端末を画面の一覧に必ず表示し、切断できるようにしている。受け付けを止めることも、合言葉を作り直すこともできる

## 5. 通信プロトコル

ホストと端末は、DataChannel の上で JSON のメッセージをやり取りする。定義は [`src/lib/charms/protocol.ts`](../src/lib/charms/protocol.ts)。

### 端末 → ホスト

| type | 内容 |
|---|---|
| `register` | 役割と名前を名乗る（開通直後に1回）。前につながっていた端末は、そのときの ID と合図（`resume`）を付ける |
| `rename` | 端末の名前を変える |
| `status` | 自分の状態を知らせる（映像を出せるか、録画中か、画質、音声の有無・消音・送り方、モニターが音を出しているか、ズームの範囲と値、ライト、通信の状態のまとめ など） |
| `route` | モニターの本番または予告に、映像を選ぶ（スイッチャーのみ） |
| `take` | 予告の映像を本番に出す（スイッチャーのみ） |
| `layout` | モニターの画面の作り方（1画面・ワイプ・2画面・テロップ重ね）と、重ねる映像を選ぶ（スイッチャーのみ） |
| `camera_control` | カメラを遠隔操作する（スイッチャーのみ）: 画質、カメラの切り替え、マイクの消音、音の送り方、ズーム、ライト |
| `monitor_control` | モニターを遠隔操作する（スイッチャーのみ）: 音を出す・消す |
| `cue` | カメラ・テロップの担当者の画面に、指示を表示する（スイッチャーのみ） |
| `record_all` | 全端末の録画を、まとめて始める・止める（スイッチャーのみ） |
| `signal` | 映像接続の打ち合わせ（SDP）を相手に届けてもらう |
| `link_failed` | 映像接続が切れたことを知らせる |

### ホスト → 端末

| type | 内容 |
|---|---|
| `registered` | 割り当てた ID と名前、次につなぎ直すときのための合図（`token`） |
| `bye` | ホストの側から接続を終える合図（`removed`: ホストが切断した / `replaced`: 同じ端末が別の接続でつなぎ直した）。受け取った端末は、自動ではつなぎ直さない |
| `snapshot` | いまの状況の全体（端末の一覧、各モニターの本番・予告、設定、開いているルームの合言葉）。変化のたびに全端末へ配る |
| `make_offer` | 「この端末へ映像を送り始めて」という指示（送る側へ） |
| `drop_link` | 「この端末との映像接続を切って」という指示 |
| `signal` | 取り次いだ打ち合わせ（SDP） |
| `camera_control` / `monitor_control` | 取り次いだ遠隔操作（録画の開始・停止を含む） |
| `cue` | 指示メッセージ（送った人の名前つき） |

ホストは、送り主の役割を確かめてから処理する（切り替えの指示はスイッチャーからのものだけ受け付ける。打ち合わせは、実際に張ろうとしている接続のものだけ取り次ぐ）。

### つなぎ直し

- ホストは、端末が最初につながったときに乱数の合図（`token`）を渡す。端末はそれを、そのタブの中にだけ保存する（`sessionStorage`）
- 接続が切れた端末のことを、ホストは覚えておく（最大64台）。映したい内容の表も、いない端末の分を残しておく
- 端末が戻ってきて、ID と合図が合っていれば、ホストは同じ ID・同じ名前を割り当て直す。映像の割り当ても元に戻る（モニターなら映していた映像が、カメラなら映されていたモニターに、また出る）。つなぎ方は QR でも合言葉でもよい
- 端末は、ホストのルームの合言葉を `snapshot` で知っている。接続が切れたら、ルームを通して自動でつなぎ直す（QR でつないだ端末も、インターネットがあれば自動で戻る）。ページを読み込み直したときも同じ
- 自動でつなぎ直している間、カメラやテロップの画面はそのまま出し続ける（撮影や録画を止めない）
- ホストが自分で切断した端末は、覚えておかない。その端末も自動ではつなぎ直さない

## 6. 映像接続

実装は [`media-links.ts`](../src/lib/charms/media-links.ts)（各端末）と [`host.svelte.ts`](../src/lib/charms/host.svelte.ts)・[`routing.ts`](../src/lib/charms/routing.ts)（ホスト）。

### 6.1 2種類の映像

| 種類 | 送り先 | 内容 |
|---|---|---|
| 確認用（thumbnail） | ホスト、全スイッチャー | 縦 180 ピクセル・10 コマ/秒・最大 150 kbps。音声なし |
| 本番用（program） | モニター | 選んだ画質。音声あり |
| インカム（talk） | 聞く設定にしたカメラ・テロップ | スイッチャーのマイクの声だけ（映像なし）。7.2 を参照 |

確認用を極端に軽くしてあるので、スイッチャーを何台つないでも、カメラ端末の負担はほとんど増えない。

### 6.2 ホストによる調整

ホストは、状況が変わるたびに「いま必要な映像接続」を計算する。

- 映像を出せる状態のカメラ・テロップ → ホストと全スイッチャー（確認用）
- 各モニターの本番と予告に選ばれた入力、重ねる（並べる）映像 → そのモニター（本番用）

実際の接続と比べて、足りないものは `make_offer`、不要なものは `drop_link` を出す。

### 6.3 接続の手順

```
ホスト → 送る側 : make_offer { targetId, profile }
送る側 → ホスト → 受ける側 : signal（Offer）
受ける側 → ホスト → 送る側 : signal（Answer）
以降、送る側と受ける側が直接つながる
```

ICE 候補は、収集が終わってから SDP に含めてまとめて送る（LAN 内では一瞬で終わる）。STUN / TURN の一覧（4.7）が手元にあれば、映像接続にも使う。

### 6.4 途切れへの備え

- **映像の差し替え**: カメラの切り替えや画面共有のやり直しでは、接続を張り直さず、映像だけを差し替える（`replaceTrack`）
- **接続が切れたとき**: 端末が `link_failed` を送り、ホストが少し待ってから張り直す（1秒、2秒、4秒…最大15秒の間隔で繰り返す）
- **切り替えの瞬間**: 「すぐ切り替える」で別の映像にしたとき、ホストは前の映像との接続を 2.5 秒残す。モニターは新しい映像の絵が出るまで前の映像を映し続けるので、黒い画面が挟まらない
- **ホストが落ちたとき**: 端末同士の映像接続はそのまま残る。モニターは映像を出し続け、つなぎ直しを案内する

### 6.5 音声

音声は、本番用の映像と一緒に送る（確認用の映像には付けない）。実装は [`audio.ts`](../src/lib/charms/audio.ts)。

| 送り方 | マイクの音の加工 | 圧縮（Opus） | 向いている場面 |
|---|---|---|---|
| 会話向け（初期値） | 雑音の除去・回り込みの除去・音量の自動調整を使う | モノラル・最大 64 kbps | 司会、説明、会話 |
| 音楽向け | すべて切る | ステレオ・最大 256 kbps | 演奏、歌、会場の音 |

- **しくみ**: ブラウザは、相手の Answer に書かれた条件に従って音声を圧縮する。受ける側は Answer に「ステレオで受け取れる」（`stereo=1`）と書き足しておき、送る側は届いた Answer を、いまの送り方に合わせて読み替える（音楽向けなら `stereo=1`・`maxaveragebitrate`、会話向けなら `stereo` を外す）。あわせて送信側の上限ビットレートを設定する。受ける側の書き足しを受け付けないブラウザでは、書き足さない Answer を使う（モノラルで受け取る）
- **切り替え**: 圧縮の条件は接続を張るときに決まるので、送り方を変えると、音声を送っている接続だけを張り直す。映像と音が一瞬途切れる
- **マイクの切り替え**: 映像はそのままで、マイクだけを開き直して差し替える（`replaceTrack`）
- **消音**: マイクを閉じずに、音を送らない状態にする（解除したとき、すぐ音が戻る）。カメラの画面からも、スイッチャーからもできる
- **音量メーター**: カメラの画面に、送っている音の大きさを表示する（-60 dB〜0 dB を 0〜100 に直したもの）
- **モニター**: 音は最初は消してある。モニターの画面、またはスイッチャーから、モニターごとに出す・消すを切り替える。ブラウザによっては、そのページを一度も操作していないと、遠隔からの操作では音が出ないことがある
- **画面共有**: 共有するときに「音声も共有」を選ぶと、その音を送る（加工はもともとかからない。ステレオ・ビットレートは送り方に従う）
- 選んだ送り方は、カメラの端末に保存される

確認の範囲: 音楽向けでステレオ・256 kbps の条件になること、受ける側の書き足しが受け付けられることは、Chromium の自動テストで確認した。実機（Windows、Android、iPhone）でも音声が届くことを確認した。音質を測定して比べることはしていない。Firefox は未確認。

### 6.6 通信の状態

実装は [`stats.ts`](../src/lib/charms/stats.ts)。各端末が、自分の映像接続を2秒ごとに調べる（`getStats`）。

| 項目 | 内容 |
|---|---|
| 経路 | 直接（端末同士）か、中継（TURN サーバー経由）か。選ばれている経路の、どちらかの端が中継用の候補なら「中継」 |
| 通信量 | 映像のデータ量（前回からの増え方で計算） |
| コマ数・大きさ | 実際に送っている（受けている）映像 |
| 遅延 | 相手との往復にかかる時間 |
| 欠け | 届かなかったデータの割合 |
| 画質を下げている理由 | 端末の処理が追いつかない（cpu）か、回線が細い（bandwidth）か。送る側のみ |

評価は3段階: **不安定**（欠け 5% 以上、または遅延 400 ミリ秒以上）、**やや不安定**（欠け 1% 以上、または遅延 150 ミリ秒以上）、**良好**（それ以外）。コマ数や「画質を下げている理由」は評価に使わない（動きのないテロップはコマ数が少なく、確認用の映像は意図して画質を絞っているので、正常でも異常に見えてしまうため）。しきい値は一般的な目安から決めたもので、この環境での実測にもとづく調整はしていない。

- カメラとモニターの画面で、相手ごとの表を見られる
- 端末全体のまとめ（いちばん悪い接続の評価と、中継を使っているか）は、**変わったときだけ**ホストに知らせる。ホストとスイッチャーの画面では、良好でないとき・中継のときだけ表示する

### 6.7 カメラのズームとライト

実装は [`camera-controls.ts`](../src/lib/charms/camera-controls.ts)。ブラウザがカメラの能力として「ズームできる範囲」「ライト」を知らせてくる端末でだけ、カメラの画面とスイッチャーに操作が出る（`getCapabilities` / `applyConstraints`）。Android と iPhone の実機で、ズームとライトの両方が動くことを確認した（2026年11月）。PC につないだカメラの多くは対応していない。自動テストのカメラはズームに対応していないため、自動テストで確かめているのは、範囲の読み取りと指示の出し方まで（単体テスト）。

## 7. 切り替え

モニターごとに、**本番**（いま映している映像）と**予告**（次に映す映像）を持つ。

| 操作 | 動作 |
|---|---|
| すぐ切り替える | 選んだ映像を本番にする |
| 予告に入れる | 選んだ映像を予告にする。モニターの表示は変わらないが、映像はあらかじめモニターに届く |
| 切り替える（TAKE） | 本番と予告を入れ替える。映像はすでに届いているので、一瞬で切り替わる。もう一度押せば元に戻る |
| 何も映さない | 本番を空にする（黒い画面） |

対象は「すべてのモニター」か、選んだモニター。スイッチャーとホストの両方から操作できる。

### 7.1 画面の合成

モニターごとに、本番の映像に加えて、もう1つの映像を出せる。

| 作り方 | 画面 |
|---|---|
| 1画面（初期値） | 本番の映像だけ |
| ワイプ | 本番の映像の右下に、もう1つの映像を小さく（幅の 28%）、白い枠を付けて重ねる |
| 2画面 | 本番の映像を左半分、もう1つの映像を右半分に並べる |
| テロップ重ね | 本番の映像の上に、もう1つの映像の明るい部分だけを重ねる。テロップは黒地に明るい文字なので、黒が透けて文字だけが残る |

- 合成は**モニターの端末が行う**（送る側は何も変わらない）。重ねる映像にも、本番用と同じ映像接続を張る
- 重ねている映像も、カメラ側では「本番中」（赤）と表示する
- 音は、本番（下地）の映像のものだけを出す
- 重ねる映像は予告を通さず、選んだ時点で出る。絵が届くまでは、1画面のまま待つ
- モニター側の録画にも、同じ作り方で描き込む
- テロップ重ねは、明るい部分を足し合わせる方式なので、白っぽい映像の上では文字が見えにくい

カメラとテロップの画面には、自分の映像の使われ方が帯で表示される（タリー）: 本番中は赤、予告は緑、どこにも出ていなければ灰色。

### 7.2 スタッフの連携

**指示メッセージ**: スイッチャー（またはホスト）から、カメラ・テロップの担当者の画面に文字を出す。送り先は全員か、1台。よく使う指示のボタン（「寄って」「引いて」など）と、自由な文（60 文字まで）。受け取った端末は、画面の上に大きく表示し、震えて知らせる（対応端末のみ）。「了解」を押すか、20 秒たつと消える。モニターには送らない。

**インカム**: スイッチャーの担当者の声を、カメラ担当に届ける。

- スイッチャー端末で「インカムを入れる」と、その端末のマイクを開き、状態（`talking`）をホストに知らせる
- カメラの画面で「インカムを聞く」をオンにした端末（`listening`）にだけ、ホストが声の接続（`talk`）を張らせる。声はスイッチャーからカメラへ直接届く。モニターには流れない
- 初期値は「聞かない」。カメラ端末のスピーカーから声が出ると、その声がカメラのマイクに入って本番の音に混ざるため、イヤホンを付けてからオンにしてもらう
- 声は一方向（スイッチャー → カメラ）。カメラ担当から返事はできない
- ホストの画面からはインカムを使えない（ホストの端末で使いたいときは、同じ PC の別のタブでスイッチャーを開く）

**録画の一斉開始・停止**: ホストが録画を許可しているときだけ、スイッチャーとホストの画面に操作が出る。映像を出しているカメラ・テロップと、すべてのモニターに、録画の開始（停止）を指示する。遠隔で始めた録画は、その端末で画面を操作していないので保存先を選べず、メモリにためて、止めたときにダウンロードする（長時間の録画には向かない）。

確認の範囲: 3つとも Chromium の自動テストで確認した（インカムは、声の接続が聞く設定の端末にだけ張られることまで）。実機でも動作を確認した。インカムの遅れの長さは測っていない。

## 8. 画質と台数の目安

映像は送り先ごとに別々に圧縮されるので、1台のカメラを同時に映すモニターが増えるほど、カメラ端末の負担が増える。

| 画質 | 解像度・コマ数 | 本番用1本の上限 | 同時に映せるモニターの目安 |
|---|---|---|---|
| 軽い | 480p・15 コマ/秒 | 0.5 Mbps | 8台 |
| 標準（初期値） | 720p・30 コマ/秒 | 2.5 Mbps | 3台 |
| 高画質 | 1080p・30 コマ/秒 | 5 Mbps | 1台 |

「モニターの目安」は、性能の低い端末（Surface SE 相当）を想定した、CHARMS 仕様書 v1.1 の見積もりにもとづく値で、このリポジトリでの実測値ではない。目安を超えると、カメラの画面に注意が出る。

ネットワークの帯域は、1 GbE の LAN であれば全カメラが高画質でも不足しない（例: カメラ8台がそれぞれ高画質でモニター2台に送っても、合計 80 Mbps 程度）。

## 9. 録画

- ホストの設定「録画を許可する」がオンのときだけ、各端末に録画ボタンが出る（初期値はオフ）
- **カメラ・テロップ**: 自分が送っている映像を、そのまま録画する
- **モニター**: 画面に出している映像を、切り替えをまたいで1本の映像として録画する（映像をキャンバスに描き写し、音声をつなぎ替えながら録る）
- 保存先を選べるブラウザ（PC の Chrome / Edge）では、ディスクに直接書き込む。それ以外では、止めたときにダウンロードする
- 録画中の端末は、ホストとスイッチャーの画面に「録画中」と表示される

## 10. オフラインでの利用

- アプリ本体は静的なファイルとして書き出す。配信元の Worker が受け持つのは `/api/` 以下だけで、アプリは `/api/` に届かなくても動く
- サービスワーカーは `/api/` 以下を保存しない（STUN / TURN の認証情報は毎回取り直す）
- サービスワーカーが、初回にアプリの全ファイルを端末に保存する。以降は保存済みのファイルを使うので、インターネットなしで起動できる
- 画面の自動消灯を防ぐ（Wake Lock）。つながっている間にページを閉じようとすると、確認が出る

## 11. 動作環境と制約

| 項目 | 状況 |
|---|---|
| Chrome / Edge（PC） | 自動テストで確認済み（Chromium） |
| Chrome / Edge（Windows の実機） | 確認済み（ホストとモニターとして使用。2026年11月） |
| Android | 実機で確認済み（カメラとして使用。ズーム・ライトを含む。2026年11月） |
| iPhone | 実機で確認済み（カメラとして使用。ズーム・ライトを含む。2026年11月） |
| iPad / Mac の Safari、Firefox | 標準の仕組みだけで作ってあるが、実機での確認はまだ |
| 有線 LAN、端末間通信を止めていない Wi-Fi | 動作する（インターネット不要） |
| 端末間通信を止めている Wi-Fi（学校の管理 Wi-Fi など） | インターネットにつながっていれば、STUN / TURN 経由で動作する（学校のネットワークで確認済み。下の行）。つながっていなければ動作しない |
| 別々のネットワークにいる端末同士 | インターネットにつながっていれば動作する。iPhone（スマホの回線）と Windows（学校のネットワーク）の間で、合言葉でつながり、TURN 経由で映像が届くことを確認済み（2026年11月）。公開先の自動確認（`npm run smoke`）でも、中継だけでつながることを確かめている |
| 多い台数（カメラ・モニター各5台以上） | 実機では未確認。目安は 8 章 |

mDNS について: ブラウザは、カメラの許可がないページでは IP アドレスを隠し、`xxxx.local` という名前を使う。CHARM Point は、QR の読み取りでカメラの許可をもらってから接続情報を集めるので、通常は実際の IP アドレスが QR に入る。カメラを使えない端末では `.local` の名前が入り、ネットワークによっては名前を引けずにつながらないことがある。

## 12. 運用上の注意（ホストについて）

ホストは全端末の制御の中心で、その状態（端末の一覧、各モニターの本番・予告）はホストのページの中にだけある。

- ホストのページを閉じたり再読み込みしたりすると、全端末がつなぎ直しになる。映像は出続けるが、つなぎ直すまで切り替えはできない
- ホストは、状況（合言葉とその鍵、端末の一覧と合図、映したい内容、設定）を、変化のたびにその端末のブラウザに保存する（`localStorage`）。12時間以内に同じ端末・同じブラウザで開き直すと、続きから再開する
  - インターネットがあるとき: 端末がルームを通して自動で戻り、映像の割り当ても元に戻る（自動テストで確認。数秒）。端末が戻った直後に、映像が一瞬途切れる
  - インターネットがないとき: 各端末と QR を読み取り直す。同じ名前・同じ割り当てには戻る
- 別の端末でホストを開き直した場合は、保存した状況がないので、最初からつなぎ直しになる
- ホストの端末は、電源につなぎ、スリープしないようにし、操作する人以外が触れない場所に置く

## 13. CHARMS 仕様書 v1.1 からの変更点

| 項目 | v1.1 | この版 |
|---|---|---|
| QR の中身 | JSON（IP・ポート・ufrag・pwd・フィンガープリント） | バイナリパケットを Base45 にしたもの（候補を最大6件） |
| QR の手順 | ホストが Offer → 端末が読んで Answer → ホストが読む（順番が決まっている） | 両方が同時に出して読み合う（順番は自由） |
| Safari 用の SDP テンプレート | ブラウザを判定して切り替え | 自分側の SDP を書き換えないので不要 |
| 映像の送り方 | 全員に同じ画質 | 確認用（軽い）と本番用を分ける |
| 切り替え | すぐ切り替えるのみ。切り替えのたびに接続を張り直す | 予告 → 本番の2段階も選べる。予告はあらかじめ接続しておく |
| 画面の合成 | なし | ワイプ・2画面・テロップ重ね |
| スタッフの連携 | なし | 指示メッセージ、インカム、録画の一斉開始・停止 |
| 通信の状態 | なし | 相手ごとの経路・通信量・遅延・欠けを表示 |
| 連打への対策 | スイッチャー側で3秒間ボタンを止める | ホストが必要な接続を計算し直すので不要 |
| テロップ | （実装では）文字をメッセージで送り、モニターが描く | 文字を描いた映像を送る（カメラと同じ扱い）。歌詞の送り出しとタイムテーブルを追加 |
| 音声 | 送る（モニターは常に消音だった） | 送る。モニターごとに「音を出す」を選ぶ（スイッチャーからも操作できる）。マイクの選択・音量メーター・消音、音楽向けの音質 |
| 録画 | なし | カメラ側・モニター側。ホストで一括して許可／禁止 |
| ホストが落ちたとき | 全接続が切れる | 映像は出続ける（切り替えだけができなくなる）。開き直すと続きから再開し、端末は自動で戻る |
| つなぎ方 | QR コードのみ | QR コードに加えて、合言葉・招待リンク（インターネットがあるとき） |
| 端末がつなぎ直したとき | 新しい端末として扱う | 同じ ID・名前・映像の割り当てに戻す |
| 同じ端末でのホストとスイッチャー | なし | QR なしでつなげる |
| フィンガープリントの保存（IndexedDB） | 最適化として記載 | していない（毎回新しい証明書で問題なくつながるため） |
| IP アドレスの手動入力 | 接続失敗時に表示 | していない（候補を複数入れることで代替） |
| インターネットの利用 | 使わない（LAN 専用） | なくても動く。あれば STUN / TURN で、直接通信できない端末同士もつなぐ |
| 配布 | 未定 | Cloudflare Workers（`charmpoint.nifty1130.com`） |
